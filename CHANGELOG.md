# Changelog

## 0.0.14

05 now takes work past the landing branch: it promotes between environments under your rules, confirms the deploy and goes back when it fails, lands hotfixes, and holds environments to those moves in CI. It also says how much each verdict rests on, keeps the CI runner key out of a branch's reach, and handles monorepos, Git LFS and owners of paths. Upgrading: run `use05 init --ci github` again to move to the new pair of CI workflows (see "Moving from an earlier setup" in `docs/turn-on-the-ci-gate.md`), and set `[use05] min_version = "0.0.14"` in a policy that uses anything below.

- **Security: an agent's branch can no longer read the CI runner key.** The workflow `init --ci github` wrote before ran from each pushed branch's own copy with the runner key, so an agent's push could change it to read the key. `init --ci github` now writes two workflows: `05.yml` runs for every push and pull request with no secret and a read-only token, and only starts `05-gate.yml`, which GitHub runs from your default branch. The gate alone gets the key, from a `use05` environment only the default branch may use; it checks out the exact commit, runs the change's checks as a separate user (`use05-check`) that cannot read the key, and posts its verdict as the commit status `05`. Post that status with your own GitHub App (`USE05_APP_CLIENT_ID`): with the workflow token a branch can forge it, and the job summary says so. Require `05` from your app in branch protection instead of `acceptance`. Install toolchains system-wide, pinned in `05-gate.yml`, in the step before the checkout; the change's own dependencies are installed by the check command itself, as the check user. The check user cannot reach the runner's home, and a command it cannot reach is not started rather than failed. On a private repository, environments need GitHub Pro, Team or Enterprise. A new policy locks `.github/workflows/**`. Where the key still reaches a branch's own workflow, the gate warns `CI_KEY_EXPOSED` and `use05 doctor` names the file. To move, follow "Moving from an earlier setup" in `docs/turn-on-the-ci-gate.md`, then rotate the runner key.

- **A refused receipts push heals itself.** When the remote holds receipts this machine lacks (two machines of one signer, or two CI jobs finishing together), 05 fetches them, merges them into the local receipts branch without touching your work tree and pushes again, up to five times. Any other push failure still stops at once, now with git's reason instead of its `To <url>` line. On one machine, agents working at once share the receipts branch; a record written while another was being written lost the race and was dropped (found with three agents at once: a sealed declaration never reached the branch). It is now written again on the branch as the other left it.
- **The record types are stable.** From this version a `…/v0` record type only gains optional fields; anything breaking becomes `…/v1`, and every later 05 verifies every earlier type. Each type has a JSON Schema in `docs/receipts`, checked against the code by a test. Receipts are never pruned and their branches never force-pushed.
- **Everything GitHub-specific sits behind one host boundary.** The CI gate and `init --ci github` read the event, push receipts, write the job summary and produce the workflow through one adapter, so another Git host can be added without touching the gate. Nothing changes for you. `docs/extending.md` has the boundary and a sketch of GitLab.
- **Git LFS files can be checked as the real files.** Checks run on exactly what is committed, which for an LFS file is its small pointer; the brief now says so under Unknowns ("2 LFS files were checked as pointers"). With `[evidence] lfs = true` (and `min_version = "0.0.14"`), 05 fetches the real files into its copy of the tree before the checks run, verifies each against its pointer, and lists their paths, object ids and sizes in the receipt. It stops with `LFS_UNAVAILABLE` if git-lfs is missing and `LFS_FAILED` if a file cannot be fetched. Line endings and other filters are still never applied. Each file gets five minutes to fetch (`USE05_LFS_TIMEOUT_SECS`), and an ssh LFS endpoint does not stop at a prompt (unless you set `GIT_SSH_COMMAND` or `core.sshCommand` yourself). The pre-push hook `init` writes now runs `git lfs pre-push` first when the repository uses Git LFS, so 05's hook no longer keeps LFS files from being uploaded, and stops the push, as Git LFS's hook does, if git-lfs is not on PATH; `init` replaces Git LFS's own standard hook with it, and `use05 doctor` warns when an LFS repository's hook does not run LFS. See "Git LFS" in `docs/guide.md`.
- **A monorepo keeps one policy, and a check can be limited to the packages a change touches.** A `[[check]]` can name `paths`: it is required only when the change touches one of them, and otherwise the brief lists it as "not required: no change in its paths" and it never blocks. It can also name `dir`, the folder of the checked tree it runs in (a folder outside the tree is refused with `CHECK_DIR_OUTSIDE`); the receipt records it. `use05 init` reads npm, pnpm and yarn workspaces, Cargo, Go and uv workspaces from their manifest files (no network, no package manager run) and suggests one check per package, with the package's folder, the root files that define the workspace and the root lockfile as its `paths` (a top that is itself a package keeps its `test` check, required for every change); the CI gate then proves only the checks a change calls for, a `dir` that is not in the tree fails that one check, and the brief notes changed files that no check's `paths` cover; it asks once whether to use them, and `--defaults` does. A policy that uses these needs `min_version = "0.0.14"`, which `init` writes. See "Monorepos" in `docs/guide.md`.
- **Paths can have owners.** Name groups of people with `[[signer]]` (`name`, `people`) and give paths owners with `[[protect.owner]]` (`paths`, `signers`, `min`, 1 by default). A change to those paths then needs, besides the approvals it needs anyway, approvals of its outcome from `min` different owners; the brief reports `OWNER_APPROVAL_REQUIRED`, names who may approve, lists under Owners who did, and says when an approval came from someone who is not an owner (`OWNER_APPROVAL_NOT_COUNTED`). People are known only by the `person` on their keys in the policy, never by git's `user.name`; two keys of one person are one owner, and a driver who is an owner covers both with one approval. An owner reads someone else's work with `use05 brief --rev origin/<branch>` and approves the commit it shows with `use05 approve --outcome --rev <commit>`, at the terminal. Only one of its owners can bypass an owner rule, and one person must own every owner rule a bypass clears. A name that is neither a group nor a person with a trusted key stops the policy from loading (`UNKNOWN_SIGNER`), as does a group with a person's name (`SIGNER_NAME_TAKEN`). Adding people to a group, adding a group with a name a rule uses, lowering `min` or removing a rule loosens the rules, which the console refuses; give `.05/**` an owner so changes to the rules need one too. An organisation floor can add groups and rules; its rules count only the people its own groups name, and only through its own keys, never a key the repository lists. A policy that uses these needs `min_version = "0.0.14"`. See "Owners of paths" in `docs/guide.md`.
- **A promotion can be judged before anything moves.** The new `use05 promote <env> --check` judges promoting into an environment from the one below it, and `use05 brief --promote <env>` is its one page: what would move (commits, files, areas), each rule and its result, who must sign off, and the next command. Nothing moves and nothing is pushed; both fetch the branches and receipts from origin first, and an agent may run them. The rules come from the policy on the target's own branch. Each environment can now say where it is promoted `from`, `how` (fast-forward or merge), whether an `agent` may promote (by default on every rung but the last), and how strongly six rules hold (`[environment.rules]`: the source's checks passed on its exact head, the source confirmed running it, `soak_minutes`, migrations, commits that belong to no task, a person's sign-off), with `[environment.sign_off]`, `[[environment.confirm]]` and `[environment.bypass]`. Always on: a target with commits the source lacks is refused, and only the evaluated commit is promoted. A name that does not exist stops the policy from loading (`UNKNOWN_ENVIRONMENT`, `UNKNOWN_SIGNER`), as does `on_failure = "command"` without a `rollback` command. Three new record types describe promotions, deployments and sign-offs (`promotion/v0`, `deployment/v0`, `signoff/v0`), each with a JSON Schema; deployment, finish and promotion records count only from keys `[evidence] accept` takes, so with `accept = ["runner"]` those rules rest on CI. A finish now records where its work meets the landing branch (`base`), and marks as the task's only the commits from there to where it finished, stopping at other tasks' finishes and promotions. Re-running `use05 init` or `use05 policy --edit` keeps every promotion setting. A policy that uses these needs `min_version = "0.0.14"`; one that does not keeps its digest. See "Environments and promotion" in `docs/guide.md`.
- **`use05 promote <env>` moves it.** When the rules allow, 05 makes the fast-forward, or with `how = "merge"` a merge commit in a temporary worktree, never in your checkout; judges it once more against the commit it showed; pushes the branch to origin, never by force and through the pre-push hook; and only then signs a promotion record and pushes it on the receipts branch. A merge commit ends with the promotion's summary as git trailers (`05-Promotion`, `05-Source`, `05-Rules`, `05-Signed-off-by`, `05-Bypass`); a fast-forward makes no commit, so its summary is only in the record. A refused push says why in git's own words and the hook's first finding (`PROMOTE_PUSH_FAILED`, exit 4) and leaves origin, your branches and the records as they were; a push whose record did not reach origin says so (`PROMOTED_WITHOUT_RECORD`) with the command that puts it there. The pre-push hook judges a push to an environment's branch as that promotion, by its rules, and holds anything but the exact move they judged, so a hand push of `uat:prod` is held by the same rules, a push it cannot judge is held (`PROMOTE_NOT_JUDGED`), and where people promote the push must come from a person at a terminal; the landing branch keeps the task gate. Deleting an environment's branch or a kept one is held unless a person does it at a terminal (`ENVIRONMENT_DELETE_HELD`), and the agent hooks refuse it. Held back, it exits with the decision, as `--check` does. Where an environment says `agent = false` (by default the last rung) only a person promotes: at a terminal, with no agent session, and with their own key, which signs the record too; in CI, a pipe or with `--json` it is refused (`NEEDS_A_PERSON`), and the agent hooks hold the command. A finish's base is now where the work meets this machine's or origin's landing branch, whichever is nearer the work.
- **Sign off on a promotion, or break glass for one rule.** `use05 approve --promote <env> --note "<what you checked>"` signs a person's sign-off (`--reject --reason` their no) bound to the environment, the source commit and the policy; at a terminal it asks each question and statement to confirm unless `--answer` and `--confirm` give them, refuses words shorter than `min_length` and a sign-off that would not count, and works with a passkey through `--unsigned` and `--signed`. `use05 bypass --promote <env> --rule <name> --reason "<why>"` bypasses one rule for that exact commit; it is refused for rules in `[environment.bypass] never`, where `allowed = false`, for a short reason, for a person's rejection and for what is built in (`BYPASS_NOT_ALLOWED`). Both are refused under an agent and without a terminal (`NEEDS_A_PERSON`, exit 3; `use05 discard` now exits 3 for it too, instead of 6). A promotion's bypass is bound to the policy and lasts 72 hours at most. The bypass record (`bypass/v0`) gains optional `env`, `from`, `rule` and `policy_sha256`. The agent hooks now also catch `use05` run through `npx`, a variable assignment, `command`, a full path or `sh -c`.
- **05 confirms the deploy, and goes back when it is not.** Give an environment probes (`[[environment.probe]]`: a command that prints the commit it runs, in full or by 12 or more characters, with `env`, `dir`, `timeout_secs`, `wait_minutes`, 10 by default, and `interval_secs`, 15) and smoke checks (`[[environment.smoke]]`, shaped like a check). After a promotion pushes, 05 asks each probe until it shows the commit or the wait is over, runs the smoke checks once, and files a signed deployment record; `--no-wait` leaves that to `use05 promote <env> --confirm`, which CI can run. They run like checks, in a copy of the deployed commit with a scrubbed environment. With no probe 05 never says a deploy is confirmed: it says "no probes: 05 cannot tell what prod runs", and a promotion from there fails `source_confirmed`. A deploy that is not confirmed is reported (`DEPLOY_NOT_CONFIRMED`, exit 2) with the one command to go back; with `on_failure = "revert"` 05 pushes a new commit holding the rollback point's files (never a force-push) and confirms that once, and with `on_failure = "command"` it runs your `rollback`, as the rollback point has it and in its files, with `USE05_ENV`, `USE05_ROLLBACK_TO` and the variables `rollback_env` names (`rollback_timeout_secs`, 900 by default). Where people promote, 05 does not revert by itself; it names the command. It goes back only to a point in the branch's own history. `use05 promote <env> --rollback` makes the same revert by hand; where people promote, only a person at a terminal may, and the agent hooks hold it. The pre-push hook lets such a revert through and still holds anything else. The promotion record gains an optional `reverts` for a revert's own record. Changing a probe, a smoke check or the rollback command counts as loosening the rules. See "Confirming the deploy" in `docs/guide.md`.
- **A hotfix lands straight on an environment, and is merged back down.** `use05 start --hotfix prod "<title>"` checks out a new working branch at origin's prod, judged by prod's rules; an agent may start one. Landing it always needs a person's approval of its outcome given for this hotfix (`HOTFIX_NEEDS_APPROVAL`): the approval records the environment and task (`hotfix` on `approval/v0`), so an approval of the same tree given for anything else never counts, and no setting, plan approval or bypass replaces it. Prod's `[environment.sign_off]` signers and word count apply to it: an approval in fewer words than its `min_length` is refused before anything is signed (`HOTFIX_WORDS_TOO_SHORT`), and where prod asks questions or statements, `use05 approve --promote prod --hotfix` gives them, so such a hotfix takes both signatures. What lands must be the hotfix's own commits: a merge, or a commit already on another environment's branch or where work lands, is refused (`HOTFIX_NOT_ITS_WORK`). `use05 land` lands it on prod by fast-forward; its promotion record (`direction = "hotfix"`, naming the task) is filed only once prod is on origin, and the pre-push hook lets exactly that landing through. `[environment.hotfix.rules]` sets the promotion rules for a hotfix; unset, the rules about the source allow and the others are the environment's own. Afterwards promoting into prod is refused (`PROMOTE_TARGET_AHEAD`), naming the hotfix and the next step, `use05 promote uat --back`: a merge commit of prod into uat (never a fast-forward, never forced), judged by uat's rules except those about the source, pushed through the pre-push hook and filed with `direction = "back"`; then `use05 promote dev --back`, one rung at a time. A sign-off it needs is `use05 approve --promote uat --back`, and a person can bypass one of its rules with `use05 bypass --promote uat --back`. Two that do not merge cleanly are refused (`BACK_MERGE_CONFLICT`) with nothing left behind; a merge resolved by hand that changes only the conflicted files passes once a person signs off on it (`use05 approve --promote uat --back --rev <merge commit>`). A merge back that would bring down a rollback 05 made above waits for a person (`BACK_MERGE_CARRIES_ROLLBACK`): it names the rollback and the work it undid, which would be undone below too; a sign-off on that merge back says to go ahead, or revert the rollback above first. Where an environment is kept for people, only a person merges back into it. The promotion record gains an optional `task`. See "Hotfixes and merging back" in `docs/guide.md`.
- **Promote to places outside the repository, and say where an agent may push.** A `[[destination]]` is promoted to with the same `use05 promote <name>`, `--check`, `brief --promote`, sign-offs and bypasses as an environment. With `how = "push"` 05 pushes a branch's head (`from`, by default where work lands) to another remote's `branch`, by fast-forward only and through the pre-push hook; with `how = "export"` it copies the exact committed content of the folder `from` at the evaluated head, never your working files, into another repository as one commit on top of its branch (`Sync from <commit>`, with the promotion's trailers), made and pushed from a temporary copy so nothing from there enters your repository. A folder that has not changed is `NOTHING_TO_PROMOTE`. Pushing is never forced; a refused push leaves no record (`PROMOTE_PUSH_FAILED`), and the promotion record (`how` push or export) is filed after the push. The rules are the policy at the head that goes out, and a policy there that does not name the destination moves nothing (`DESTINATION_NOT_AT_HEAD`). By default only a person promotes to a destination (`agent = true` lets an agent), and a destination has no probes, soak, rollback, hotfix or `--back`; the policy refuses those keys on one, and a name an environment also has (`DUPLICATE_TARGET`). `[push] agent = ["origin"]` lists the remotes an agent may push to, by name or URL: the agent hooks refuse an agent's `git push` anywhere else, and the pre-push hook holds it (`PUSH_REMOTE_NOT_ALLOWED`); unset, any remote, as before. Both are advisory on your machine. `use05 policy` shows both. Adding a destination or a remote counts as loosening the rules. A policy that uses these needs `min_version = "0.0.14"`. See "Destinations" in `docs/guide.md`.
- **CI holds an environment to the moves 05 makes.** On a push to an environment's branch (or a merge back onto the branch work lands on), the CI gate asks for the move's promotion record, checks it against what was pushed and against the last promotion of that environment, and judges the move again as of before the push, with the pre-push hook's own rules and code. Without a counted record the push is held (`PROMOTION_RECORD_MISSING`); a record that does not match (`PROMOTION_RECORD_MISMATCH`, `PROMOTION_CHAIN_BROKEN`, `PROMOTION_SOURCE_NOT_ON_BRANCH`) holds it too. A hotfix's landing is rebuilt from its record and its approval, and where people keep an environment the record must carry a person's co-signature. See "In CI" in `docs/guide.md`.
- **Your console shows the environments, and you can sign off from your phone.** A repository's page lists each environment: the commit its branch holds, its newest deployment record (confirmed, not confirmed, or no probes), its newest promotion, and how many commits wait to come up. Where they wait, sign off on the promotion with your words, the environment's answers and statements and your passkey; one of your own machines prepares it for the exact commit, co-signs and files it. Where the environment names no signers, it counts as your own, like the approvals your pinned passkey gives; so does a hotfix approval from it. The promotion itself still runs on a machine or in CI. See "Environments" in `docs/console.md`.
- **The setup's team sets who promotes into the last environment.** `use05 init --team solo` lets an agent promote into the last rung too (`agent = true`); `small` keeps it for people, as the default does; `regulated` also asks a person's sign-off there (`[environment.rules] sign_off = "approval"`). Only environments new to the policy get these. `use05 policy set environment.<name>.<setting>` changes one environment's setting, such as `environment.prod.rules.sign_off approval`.
- **Approving a hotfix says where it lands.** `use05 approve --outcome` on a hotfix task now says, before you sign and in its headline, that this approval lands the work straight on the environment.
- **The brief opens with the change's story.** A few lines at the top, each saying where it comes from: what was asked, what the agent says (its own words, and how many of its claims a check backs, contradicts or has nothing to say about), what 05 saw, what the checks found, what needs you (including a person's testing before a push, where the rules ask for it) and what is not known. An agent's words are never shown as a finding. `brief --json` gains `story`; the console's task page shows the same story under "What we know", without your request or the agent's words, which stay on the machine. The rest of the brief is as it was. It also says whether the tests stand apart from the change: edited by it, protected by your `[protect]` rules so only a person can change them, or not protected (`assurance.test_origin`); never that they are good.
- **The brief says how much a verdict rests on.** Under the decision, a line counts the checks required for this change and who signed them: "Checks: 1 passed on the machine that ran it (advisory: an agent can run as its user)", "Checks: 1 passed, signed by CI (merge enforcement not confirmed from here)", or the ones that failed, did not run or are stale, first. A change that edits its own test files gets a note, and "Behaviour beyond these checks: not assessed" is said every time. A change allowed with no checks says "Checks: none required; behaviour not verified", and the agent's window and the bare page add "no checks ran, behaviour not verified" beside "nothing to read"; work landed with no check run, or let through by a bypass, is no longer said to have passed its checks. `brief --json` gains one `assurance` object with the counts; every other field, every decision and every exit code is as it was. The console shows the same line under a task's verdict. It is not a score. See "What the checks line means" in `docs/guide.md`.
- **`use05 doctor` says when nothing is ever run.** A policy with no required check gets a note, also just after `use05 init` while the policy is not yet committed: 05 never runs anything to see whether a change works, so every ALLOW rests on the rules alone. It names the command to add one, with the test command it found where it found one (`use05 policy add check '{ name = "test", run = ["npm", "test"] }'`).
- **Fixed: a repository taken for using Git LFS because Git LFS once ran in it.** `lfs.repositoryformatversion`, which Git LFS writes into any repository it runs a command in, made the pre-push hook stop every push on a machine without git-lfs. Any other `lfs` setting, or a `filter=lfs` line, still counts.
- **An agent told 05 is too old is asked to stop, not to install it.** Under an agent session, a policy that needs a newer 05 now says "stop and ask the user to upgrade 05 (npm i -g @use05/cli); do not install it yourself" instead of the install commands, and the block `use05 init` adds to `AGENTS.md` says the same. Found in testing: given the commands, Codex ran the installer on the person's machine.
- **`use05 doctor` counts the receipts.** The Record section says how many receipts are stored, on how many branches, and their size (`details.receipts` in `--json`).
- **`use05 doctor` suggests settings from your own history, and WSL is documented.** From the last 30 days of this machine's record (times only), doctor suggests `drift.reservation_idle_hours` when agents go quiet for much longer or shorter than reservations last, and `evidence.stop_budget_secs` when your required checks take longer than the Stop hook may spend (or says CI proves them when they cannot fit in its 90 seconds), each with the exact `use05 policy set` command; it never changes a setting itself. It also says when agent hooks an older 05 installed lack events this version installs, and to run `use05 init`. A guided `use05 init` or `use05 policy --edit` that nobody answers for ten minutes stops with `No answer in 10 minutes; nothing was written.` (exit 1, `INIT_NO_ANSWER`). A rule set by `use05 policy set` or the guided setup now replaces its commented example (such as `# locked = []`) instead of sitting beside it. On Windows, 05 runs in WSL: the guide ("On Windows") says how, and doctor warns when the repository is on a Windows drive (`/mnt/c`), where hooks are slow.

- **A new look for the console.** The 05 logo is now a heavy, wide 05 cut by five stripes, with a red dot in the zero; the console follows it: a black rail, light grey pages, keycap buttons, Archivo and IBM Plex Mono, and red only where a person is needed. When you approve, the red dot drops into the zero.
- **CI stays green when GitHub has no Mac for it.** Pushes run the Linux tests and static build only. Releases build Linux and the console image in CI; the macOS binaries are built on a Mac with `tools/release-macos.sh vX.Y.Z --publish`, which builds both from a fresh clone of the tag (Touch ID required), adds them and a SHA256SUMS for every platform to the draft, publishes it and moves the console image's `latest`. The macOS tests run by hand in the new `macos` workflow.
- **Approving a push where it stopped shows what the push holds.** "Approve it now?" listed the files changed since the repository's last task began, which could be more than the push sends; it now counts what the push itself sends, as the pre-push hook does. The approval always bound only the pushed content.

## 0.0.13

05 now asks for less than a pull request did: nothing when the work matches its plan and its checks pass, and one action, where you already are, when it does not.

- **The verdict comes to the agent's window.** When Claude Code stops and 05 has nothing to ask of it, you see one line: whether the work landed, is allowed with nothing to read, still has checks to run, needs you (and why), or is blocked, with the one command to run. It is said again only when it changes. `hook generic` carries it as `message`.
- **Approving lands the work.** Once your approval counts and the gate allows the task's work, it lands: on its own with `[branches] land = "auto"`, with `use05 approve --land`, or after "Land it on main now?" at the terminal. An approval from your console lands it too, when the policy lands on its own.
- **Landing pushes.** After landing, 05 asks "Push main to origin now?" at a terminal; `use05 land --push` pushes without asking, and the new `[branches] push = "auto"` pushes every time. The push goes through the pre-push hook, after your receipts, so CI finds the approvals.
- **Touch ID approvals on macOS.** `use05 key new --approver` offers a key made in the Mac's Secure Enclave, used with Touch ID (or the Mac's password where there is no sensor). The Secure Enclave refuses to sign without you, so an agent running as you cannot approve. Its signatures are passkey signatures co-signed by the machine, so CI and `use05 verify` check them as they check a phone's. Break glass still needs the passphrase key; `USE05_NO_TOUCH_ID` turns it off.
- **By hand, it is commit and push.** When a push needs a person and you are at the terminal, the pre-push hook shows why and asks "Approve it now?", then lets the push go on.
- **Setup in one run.** At a terminal `use05 init` makes your approver key and offers to commit the setup; the first push asks for the one approval of 05's rules right there.
- **Working alone lands on its own.** The "just you" setup sets `land = "auto"`.
- **Rules that only cost you attention are named.** A rule that held five or more changes back for you in 30 days, all approved, shows under Tip on the bare page and in `use05 doctor`, with `use05 policy --edit`. 05 counts; it never changes a rule itself.
- **The bare page acts.** Its first menu entry is the next thing to do (approve, land, run the checks), and Enter does it.

## 0.0.12

- **Fixed: Home scrolled sideways.** A repository with a long name made its chip refuse to shrink, and the whole page grew with it. Chips now truncate and wrap, and long strings break everywhere in the content area. Checked on every page at widths from 1440 down to 320.
- **Fixed: Home listed finished work as needing you.** The machine asks again each time work changes, and every ask stayed in the console, so one long task could show eight times. Only the newest request for a piece of work is current, and work already in the landing branch asks for nothing.
- **Fixed: the same list in a different order on Linux and macOS.** Tasks touched in the same second now keep a fixed order (newest made first, then by id), and repositories tie-break by path.
- **The console image is built on its own.** It no longer waits for every platform's binary, so a macOS runner that never arrives cannot stop it. The version tag is pushed at once; `latest` moves once the release is published.
- The npm workflow runs only when started by hand. Publishing is staged with your security key, so a published release no longer starts a run that fails for want of credentials.
- The needs-you list on Home has a full border and a soft tint instead of a thick side stripe.

## 0.0.11

- **The console is one pane.** Home lists what needs you first, then what is working, then what finished lately, in tight rows, with your repositories and machines in a line each. Every inner page has breadcrumbs, so there is always a way back.
- **Fixed: times that lied.** A row said when a record was last sent to the console, so every resync made a day-old session look new. It now says when the work last changed on its machine; a day or more back reads as a date, with the exact time on hover.
- **Fixed: approved and released work shown as held.** The helper reports whether a task's work is already in the landing branch. Home shows it as **Landed** and it no longer asks for you.
- **Held work needs no terminal.** Work held for you that its machine never asked about has **Ask for my approval** and **Reject it instead…** on its page: your machine prepares the statement and your passkey signs it there. A rejection is signed only when you asked to reject.
- **Fixed: Discard that waited for ever.** The console stops waiting for a machine that does not answer after two minutes, says so, and lets you try again.
- **`use05 approve` says which task it is approving.** With several tasks waiting, a terminal shows a numbered list (no default, so Enter never approves the first); under an agent or CI it refuses with `TASK_AMBIGUOUS` and lists them. `--task <id>` still names one, and now judges that task's own checkout, not the folder you ran it in.

Inside one it is a single pane of Needs you, Working and Recent, each with its id and whether finished work has landed. ## 0.0.7

- **Your own console.** A web app you host yourself, for you or your team: see every agent's work across your machines, approve what waits for you with a passkey from your phone, tighten policies, get an email when something needs you. One image (`ghcr.io/use05-dev/use05-console`), its data one SQLite file on a volume. People join by invitation as admins or members; each machine belongs to whoever paired it, and only they approve its work. Encrypted end to end: machines seal and sign what they report to the team's key, which each person unlocks with their passkey or a recovery code; the browser opens it and builds every page, and runs the policy editor; the console sees only what it needs to route, and emails say only that something needs you. Pairing asks for a word only the machine's terminal shows, then for two codes to match, worked out on each side from the keys and a nonce from both. Removing someone makes the team a new key. Machines connect out and run nothing they are sent; policy edits from the browser may only tighten. The helper, `use05-cloud` (`use05 cloud login|add|enrol|install|status|sync`), now ships with 05 in the release archives, the installer and npm. See [Your own console](docs/guide.md#your-own-console).
- **Claim your console from the terminal.** A fresh console writes a claim code to its log; `use05 cloud login <url>` asks for it, opens a one-time link to make your passkey, and pairs the machine, so there is no setup secret to set (`SETUP_SECRET` still works). Run inside a repository, `login` also reports it, pins your passkeys and keeps running in the background. You stay signed in until an hour without using the console (links from email open it signed in), and open pages update as soon as something changes. The console speaks to you, not to a team, until you invite one; its home page counts work held for you even when no approval was asked for.
- **Approve with a passkey.** 05 accepts an approval signed by a passkey (Face ID, a fingerprint, a security key). `use05 approve --unsigned` prints the exact statement and the challenge a passkey signs, and stores nothing; `use05 approve --signed <file>` files the signed result if a key you trust as an approver signed it. Pin a passkey on your machine in `passkeys.pub` in 05's per-user directory, or list it under `[[trust.key]]` with `role = "approver"` for CI. A passkey's signature is checked for the right site, that the person was verified, and that it covers exactly the statement. Passkeys approve and reject; they cannot bypass. The receipt format page describes the signature.
- **Passkey approvals are co-signed and belong to the work's owner.** `approve --unsigned` co-signs the statement with this machine's key (`details.cosignature`), and a passkey approval counts only with a trusted machine or runner co-signature on the same statement, and only when the passkey belongs to the person who owns the work. A passkey in `[[trust.key]]` names its `person`. A page that holds a passkey can be made to sign anything; this way what it signs counts only for what a machine prepared.
- **Testing before a push.** `[testing] local = "skippable" | "required"` (and `branches`, by default the landing branch) asks that a person tried a change in their own development environment before it is pushed. `use05 approve --tested --note "…"` signs off, bound to the exact tree, with the approver key or a passkey (co-signed by the machine, for the person driving the work); `--skip-testing --reason "…"` skips where the policy allows. The pre-push hook, `use05 land` and the CI gate hold the push (`TESTING_REQUIRED`); an approval never counts as one. Which branch is the landing branch is the policy's to say (else the host's or origin's default branch), never the agent's declaration; the CI gate reads a merge queue's base branch, and holds a run that names no branch. The sign-off is its own receipt type (`https://use05.dev/testing/v0`) with the note, shown in the brief, heard by extensions as `tested`, and, with your own console, signed from a phone on the task's page.
- **Discard abandoned work.** `use05 discard <task>` throws away work an agent left behind: its worktree, its branch here and on origin, and 05's record of the task, after showing what would be lost that exists nowhere else (commits on no remote branch, files never committed). A person confirms at the terminal, or on the console's task page with a passkey (**Discard this work**), signing a discard the machine prepared; an agent can do neither. The console then forgets the task. It never deletes the landing branch or one the policy keeps, and does nothing if the work moved since. Work untouched for a week is marked as looking abandoned; nothing is deleted on its own. Extensions hear a `discarded` event.
- **Everywhere the code is worked on.** The console helper runs on Linux too (`use05 cloud install` sets up a `systemd --user` service; `status` says how it runs). `use05 init --shared-hooks` puts Claude Code's hooks in the committed `.claude/settings.json`, and a Claude Code cloud session then installs 05 and, with a token from the console in `USE05_SESSION`, reports to it. CI reports its verdict with a token in `USE05_CI` (`use05-cloud ci report`), the console shows "CI gate not seen" until it does, and work only CI sees can be approved on the console, prepared and co-signed by the runner key and filed on the next run (`use05-cloud ci collect`). `use05 approve --unsigned --approver <name>` prepares a statement for someone else to sign.
- **One rule at a time.** `use05 policy set|add|remove <setting> <value>` changes one setting or list entry (a whole rule as an inline table) and keeps the file's comments, showing before and after and saying when it loosens. In the console each rule saves on its own.
- **`approval_needed` event.** Event extensions hear when a task waits for a person's approval (after finish, when the agent stops, at the gate, or when a landing is held back): the task, the tree, whether the plan or the result needs it, and the finding codes.
- An approval counts only within `approvals.expire_days` of when it was made, and not if it is dated ahead: an approval prepared or signed elsewhere cannot give itself a longer life. The brief says why one does not count.
- `use05 verify --key` takes a passkey public key too.
- **Upgrading.** A policy using `[testing]` or a trusted key's `person` is not read by older versions; set `[use05] min_version = "0.0.7"` so they ask to be upgraded. New setups write it.

## 0.0.6

- **Fresh base.** `[branches] fresh_base` (allow, warn, approval or deny). When it is on, the hook fetches origin's copy of the landing branch as an agent's session starts, and tells the agent whether it has the latest code and, if not, how far behind it is and how to update (`git pull --rebase origin main`). Work that started behind and never caught up shows as `BASE_STALE` in the brief, and is held at the setting's strictness. When the agent updates, by rebasing or merging, the commits it pulled in are not counted as its change, including any pushed after its session started. Only a new session is checked, not a resume or compaction. The fetch gives up after 5 seconds, never asks for a password or ssh passphrase (ssh runs in batch mode unless you set your own ssh command) and leaves nothing running; a failed fetch is said and never erases or holds anything. New setups turn it on as `warn`; existing policies are unchanged until you set it. Checked on your machine; the CI gate does not re-check it.
- **Files that change together.** A `[[require]]` rule: when a change touches `when`, it must also touch `also` (for example `when = ["src/api/**"]`, `also = ["docs/api/**"]`). The agent is told the rule when its session starts; when it stops without the update (staged or not), Claude Code is asked once to make it, also after it was first asked to fix a failing check; the brief reports `ALSO_CHANGE_MISSING`, held at the rule's `severity` (`approval` by default). An optional `why` is said to the agent and in the brief. 05 checks that a file there changed, not what the change says.
- The guided setup asks which folders must be updated whenever code changes, and how strict fresh base is. An organisation floor can set `branches_fresh_base` and add `require` rules. A policy using either rule needs use05 0.0.6 or newer; older versions are told to upgrade.
- **Fixed: a scope written as one string.** `--scope "src/** docs/**"` or `--scope src/**,docs/**` is now read as two patterns, not one that matches nothing (which put every changed file outside the plan). Found when a real agent declared its plan that way. `--exclude` too.
- **Fixed: agents working in a subfolder.** When an agent's session moved two or more folders below the repository's top (`apps/web/app/...`), 05 looked for its state outside the repository. Every hook then failed with "creating the state directory: Read-only file system" and nothing was checked; from shallower folders it quietly wrote its state to a `.git/05` folder above the repository. 05 now finds the repository's own `.git` from any folder.

## 0.0.2

- **Folder and file rules.** In `.05/policy.toml`, `[protect]` can now mark paths `locked` (never changed; no approval clears it), `append_only` (new files only, for example database migrations; edits, renames and deletions are refused), `no_delete`, and `no_read` (agents may not open them). Agent hooks refuse these before they happen, through file tools and the shell; the gate and the CI gate deny them. A person can bypass a rule for one exact change with a stated reason, unless the path is listed in `absolute` or `bypass = false`. Rules are read from the change's base, so a change cannot unlock a file and edit it in one go. An organisation floor can add rules and turn bypass off. `no_read` is advisory: it holds only where an agent's own hooks report the read.

Versions before 0.0.2 cannot read this line, so everyone working on a repository set up by 0.0.2 needs 0.0.2 or newer.
- Claude Code hooks now also see Read, Grep and Glob, so `no_read` can hold. Run `use05 init` again after upgrading: it now updates hooks an older version installed, keeping other tools' hooks.
